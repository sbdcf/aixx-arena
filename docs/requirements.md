## 0. 一页速览

| # | 赛制 | 人数 | 题量 / 时长（默认） | 判分口径 | 纯静态能跑吗 | 必须后端吗 | 判分位置 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 个人客观题（校赛） | 1 | 55 题 / 60 分钟 | 55 题 100 分折算 | ✅ 完全可用 | 不需要 | 静态：前端；联机：服务端 |
| 2 | 团队个人赛（个人对抗） | 3，各自独立 | 每人 10 题 / 5 分钟 | 答对 2、答错 −1、不答 0；团队满分 60 | ⚠️ 只能单机模拟或手动对分 | 想自动汇总就需要 | 同上 |
| 3 | 团队合答（团队对抗） | 3，1 主答 + 2 辅助 | 10 题 / 15–20 分钟 | 答对 4、答错 −1、不答 0；满分 40 | ✅ 同屏一台设备可用 | 远程联机才需要 | 同上 |
| 4 | 个人接力（接力赛） | 3，依次接棒 | 每人 X 分钟 / X 题，默认 5/5 | 待配置（默认同团队对抗） | ❌ 做不了真计时 | **必须** | **服务端** |
| 5 | 团队抢答 | 3/队，多队同场 | 题量与时长为配置 | **前 50% 提交且答对者加分** | ❌ | **必须** | **服务端** |

**一句话结论**：赛制 1–3 是"一个人（或一台设备）能闭环的练习"，赛制 4–5 是"必须由服务端当裁判的对抗"。所以产品天然分层——**静态训练场（永远可用）+ 临时的对局后端（用的时候才起）**。

**官方口径说明**：赛制 4（个人接力）与 5（团队抢答）见于官方「极速对抗」环节——2025 联赛决赛「极速对抗」包含"个人接力、团队抢答与 AI 专项三类题型"（[2025 联赛报道](https://www.scjyfb.net/_wx/_wx_home_news_i.aspx?iid=639000265688643309&ret=fb&said=637128828486681831)，2025-11-28）；2026 浙江省线下决赛同样设「极速对抗」「现场答辩」两项（[浙江省大学生人工智能竞赛组委会](https://gxtgw.zju.edu.cn/2026/1019/c29187a3216685/page.htm)，2026-10-19）。**但两类赛制的题量、时长、具体计分细则，公开材料未查到**，本文按教练口述与可配置默认值实现。

## 1. 背景与目标

### 1.1 现状

- 已有备考站 `aixx-guide`（MkDocs + Material，GitHub Pages）：讲赛制、给资料、浏览题库，**但没有"真打一场"的能力**。
- 已有题目 JSON schema（`design/站点设计方案.md` §5）与 55 题原始卷（`Guide/题库（部分）.docx`）。
- 赛事事实已核实：个人对抗满分 60 / 团队对抗满分 40 / 校赛 55 题 60 分钟 / 淘汰赛按"得分 + 答题时长"排序。

### 1.2 要解决的问题

学生看得懂规则，但**没地方按规则练**。真实比赛里最致命的不是不会，是：

- 55 题 60 分钟，节奏没练过 → 做不完；
- 个人对抗答错扣分 → 敢不敢蒙、什么时候放弃，需要肌肉记忆；
- 团队对抗 10 题 15 分钟，三个人怎么分工；
- 接力的时间是"滚"的，交接慢一秒就是全队少一秒；
- 抢答慢半拍就没了，且要判断"抢了答错是否划算"。

这些只能靠**多次完整对局**练出来，看解析练不出来。

### 1.3 目标（可验收）

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | 打开网页即可完整打一场校赛模拟（55 题 / 60 分钟），交卷出分与逐题解析 | 无后端、断网可用 |
| G2 | 建房、拉人、完成赛制 2–5 中任意一种，成绩自动汇总 | 一局跑通 |
| G3 | 换题库只改 JSON、改赛制参数只改配置文件，不改代码、不重新发版后端 | 新题库丢进去即生效（热加载） |
| G4 | 从"决定练一场"到"房间开打"≤ 3 分钟，全程不注册账号 | 计时实测 |
| G5 | 刷新、误关、切后台后 30 秒内回到原对局且不丢已答内容；超时自动交卷 | 断网/刷新演练 |
| G6 | 电脑浏览器可完整完成全部流程；手机/平板基本可用 | 真机实测 |

### 1.4 非目标

- ❌ 不做正式比赛平台：不做实名认证、人脸识别、屏幕监控、成绩公证。
- ❌ 不做持久化数据库：对局结束即销毁，成绩靠导出文件留存。
- ❌ 不做 web 端题库编辑器（沿用 GitHub 提交流程 + 离线出题器）。
- ❌ 不做 App、小程序、公众号（响应式网页即可）。

### 1.5 反目标（做成了也算失败）

- 为了联机，把静态版做成"必须连服务端才能用"。
- 抢答用客户端时间戳裁决——谁的电脑快谁赢。
- 题库和赛制写死在代码里，换一届比赛重写一遍。
- 只适配手机，学生用电脑打开反而难用。
- 为了"真实"引入账号体系、数据库、后台管理，结果没人部署得起来。

## 2. 角色与场景

| 角色 | 谁 | 关心什么 |
| --- | --- | --- |
| 选手 | 参赛同学 | 练一场、看分、看解析、知道差在哪 |
| 队长 | 队内一人 | 建房/建队、拉人、开始 |
| 教练 | 社团负责人 / 老师 | 换题库、定参数、看班级整体水平 |
| 系统 | — | 计时、判分、裁决、汇总 |

### 典型故事

1. **赛前夜自测**：小林用笔记本打开站点，选"校赛模拟"，做到第 38 题去接水，回来接着做，最后交卷 71 分，看错题。
2. **三人约练团队对抗**：队长建队拿到 6 位团队码发到群里；三人各自电脑输码加入，一人主答；20 分钟到自动交卷出 28 分。
3. **练接力**：三人各就各位，第一棒 3 分 12 秒做完 5 题交棒，第二棒拿到 6 分 48 秒，第三棒只剩 5 分 00 秒——教练当场看到"第二棒吃掉了继承时间"。
4. **抢答拉练**：四队同场，题目放出后各队抢时间提交。A 队 800ms 提交且答对 → 加分；D 队 4.2s 提交且答对，但排在第四（后 50%）→ 不加分。

## 3. 核心概念（先把词定死）

| 概念 | 定义 |
| --- | --- |
| **题库 Question** | 一道题，沿用现有 JSON schema（single / multiple / judge） |
| **试卷 Paper** | 一次对局抽出的有序题目集合 + 每题分值 + 分棒结构 |
| **对局 Match / 房间 Room** | 一次完整的赛制运行：试卷 + 时间轴 + 队伍 + 结果 |
| **队伍 Team** | 1–3 人；赛制 2 每人独立答卷，赛制 3/4/5 共用一张答卷 |
| **答卷 AnswerSheet** | 一份作答记录，归属"某队"或"某人" |
| **时间轴 Clock** | 对局的权威时间事实：开始、截止、各段切换点 |
| **本地模式** | 无后端，全部状态在浏览器（localStorage / IndexedDB） |
| **房间模式** | 连后端，服务端持有权威状态、时钟与判分权 |

### 3.1 两种运行模式与能力边界

| 能力 | 静态模式 | 房间模式 |
| --- | --- | --- |
| 单人限时答题、断点续答 | ✅ | ✅ |
| 同设备多人轮流/围坐 | ✅ | ✅ |
| 跨设备同时开题（共同时钟） | ⚠️ 只能"约定时刻各自开跑" | ✅ |
| 只有主答能提交（权限） | ❌ 无法鉴权 | ✅ |
| 接力时间继承（真实计时） | ❌ 做不了 | ✅ |
| 抢答裁决（谁先） | ❌ 做不了 | ✅ |
| 成绩自动汇总 / 实时排名 | ❌ 靠手动 | ✅ |
| 判分权 | 前端 | **服务端** |
| 答案不下发客户端 | ❌ 静态必然可见 | ✅（服务端判分时） |

> **设计红线**：静态模式必须永远保留"单人部分"的完整功能。后端是增强，不是前提。

### 3.2 判分归属（v0.3 定：有服务端就以服务端为准）

**规则只有一条**：**只要房间连上了后端，判分就在服务端**；只有纯静态模式才由前端判分。

| 场景 | 判分位置 | 后果 |
| --- | --- | --- |
| 静态模式（未配置后端） | 前端 | 答案随题库包可见，属已知且接受 |
| 房间模式（已连后端，任何赛制） | **服务端** | 后端必须持有题库只读副本；客户端拿不到答案 |

**实现约束**：
- 后端启动时从 `--questions ./data/questions` 只读加载题库，支持热加载（文件变动即重载，G3）。
- 「零外部依赖」= **零数据库、零第三方服务**；题库是数据文件，不是依赖。
- 判分逻辑写成**前后端共用纯函数模块**：静态模式用它，服务端也用它，杜绝两套规则漂移（AC-11 契约测试）。
- 联机时前端只收"对/错 + 得分"，不收正确答案；解析在交卷后才下发。

### 3.3 房间拓扑与身份（v0.3 定）

```
Room（一场对局）
 ├─ format, paperId, phase, clock
 └─ teams[]（1..N 支，N 由服务端按资源上限决定）
      ├─ Team: teamId + 6 位团队码 + members[]（1–3 人）+ captainId
      └─ AnswerSheet（team 级或 participant 级，看赛制）
```

| 赛制 | 房间里的队伍数 | 答卷归属 | 说明 |
| --- | --- | --- | --- |
| 1 | 1（1 人） | 个人 | 一个人开一局 |
| 2 | 1..N | 每人一张 | 一队 3 人同房；也可多队同房各自练 |
| 3 | 1..N | 每队一张 | 只有主答能写 |
| 4 | 1..N | 每队一张 | 三棒轮流写同一张 |
| 5 | **≥2** | 每队一张 | 多队同场抢答 |

**身份模型（无账号）**
- 连上服务端 → 输入昵称 → 服务端分配 `participantId`（写入 localStorage，重连凭此恢复）。
- 团队赛：建队 → 得 `teamId` + **6 位团队码**（排除 0/O/1/I 等易混字符）；队友输码加入同一 team。
- 昵称仅存在于对局内存，不落库；对局销毁即消失。

**联机上限（服务端自行决定）**
- 后端启动时按机器资源算出实际上限并打印，可通过 `--max-teams-per-room`、`--max-connections` 覆盖。
- 默认参考值：单房 8 队 / 24 人，单实例 300 个 WebSocket（含重连余量）。
- "一场 60 队"= 多个房间并行，不是 1 个 60 队房间。

## 4. 五种赛制拆解

> 判分与时长均为**配置文件数值**，下文是默认值；教练可按届次/校情改，不改代码。
> 用户口述与官方公布不一致处标 **【冲突】** 并给默认值。

### 4.1 赛制 1 · 个人客观题（校赛）

**规则**
- 55 题 / 60 分钟（高职口径；本科口径有 50 题的说法 **【冲突】**）。
- 题型构成：单选 30 + 多选 15 + 判断 10 = 55。
- 允许开卷检索、允许使用 AI 辅助 **[校方]** → 平台**不做反作弊**，只做限时与判分。
- 多选**全对才得分，少选/错选均不得分**。

**交互（电脑为主）**
- 左侧题号面板（55 格，已答/存疑/未答三色），右侧题干 + 选项；上下题按钮 + 键盘方向键。
- 可标记"存疑"、可跳题、**可回改**；交卷前有未答提示。
- 倒计时在页面顶部常驻（最后 5 分钟变红）；时间到自动交卷。

**提交模型**：`batch` —— 答案**逐题静默上报**（客户端本地暂存 + 上报服务端保存，不回对错），交卷时统一判分。允许回改是校赛的真实体验，不能做成"点了就锁"。
> 为什么不"交卷时一次性上行"：断线 30 秒后服务端要能自动提交"已答内容"，若答案只在交卷时才上传，服务端手上就是空卷（AC-10 会得 0 分）。

**状态机**
```
未开始 → 答题中 ──交卷/超时──→ 已交卷 → 成绩页
              ↑↓ 刷新：从本地恢复（剩余时间按绝对截止时刻算）
```

**边界**
- 刷新/关页：按"绝对截止时刻 = 开始时刻 + 60 分钟"恢复，剩余时间不因刷新变多。
- 题目答案缺失（`answer_status != verified`）：该题不参与计分，交卷时明示。
- 静态模式下若怀疑题目答案有误 → 结果页一键**向题库仓库发 Issue**（见 FR-39）。

**需要后端**：否。

**默认分值**：单选 1 / 多选 2 / 判断 1（原始 70），成绩页同时显示原始分与百分制折算；可配。

### 4.2 赛制 2 · 团队个人赛（个人对抗）

**规则**
- 3 人各答各的：每人 10 题 / 5 分钟。
- 每题 2 分，答错扣 1 分，不答 0 分 → 每人满分 20，团队满分 60。
- 团队总分 = 3 人得分之和（与官方"个人对抗满分 60"一致）。

**关键体验**
- 三份卷**同题同序**（公平），同一时刻开题。
- 实时显示"队友已完成 2/3"，**不显示队友分数**。
- 答错扣分必须显眼提示：不确定时"不答"= 0，蒙错 = −1。

**提交模型**：`stream` —— 点选即锁题，立即判分并给出对错。只有锁题才让"不答"这个策略成立。

**两种跑法**
- 静态模式：单机模拟（只算自己那份），或"约定开赛时刻 + 各自作答 + 手动录分"。
- 房间模式：同房同时开题，各自独立，服务端判分与汇总。

**需要后端**：自动汇总需要；纯练习不需要。

---

### 4.3 赛制 3 · 团队合答（团队对抗）

**规则**
- 3 人一队，10 题，**15 分钟**（官方）／**20 分钟**（教练口述）**【冲突】**，默认 20 分钟、可配。
- 答对 4 分，答错扣 1 分，不答 0 分 → 满分 40。
- 一人主答，两人辅助：**只有主答能提交**。

**三种物理形态**
| 形态 | 场景 | 需要什么 |
| --- | --- | --- |
| 同屏 | 三人围一台电脑 | 静态模式即可 |
| 各看各的 | 三台电脑/平板，题面同步 | 房间模式（题面/进度同步，提交权在主答） |
| 远程 | 三人异地 | 房间模式 + 断线重连 |

**提交模型**：`stream`（提交即锁、即判）。团队合答的刺激来自"提交了就定了"。

**边界**
- 主答掉线：30 秒内连回继续；超时服务端**自动提交已答内容**，并允许队长（辅助）接管主答权，事件写进对局日志。
- 辅助误触：提交按钮只对主答渲染/生效，服务端二次校验。
- 交卷：主答提交 / 超时自动 / 服务端强制。

**需要后端**：同屏不需要；跨设备需要。

### 4.4 赛制 4 · 个人接力（接力赛，官方「极速对抗」环节）

**规则（教练口述，官方细则未查到）**
- 3 人，每人 X 分钟、X 题，**上一人剩余时间继承**。

**题目分棒**
- 组卷时切 3 段、每棒一段、**互不重复**；默认 X = 5 题，共 15 题。
- 本棒内可以反复改答案（多选可逐项勾选、改选），交棒瞬间才锁定；多选按最终所选整组判分。
- 交棒后前一棒的题**不可回看、不可修改**。
- 只显示"当前棒第 k 题"，不显示总题号（防按题号推断难度分布）。

**时间模型（本平台定义，需按官方细则复核）**

设第 i 棒可用配时 `c_i`、实际用时 `t_i`、开始时刻 `s_i`：

```
c_1 = X
c_i = X + max(0, c_{i-1} - t_{i-1})      # 只有省下的时间能继承，超时不倒扣下一棒
e_i = s_i + t_i                           # 交棒时刻，停表即交
s_{i+1} = e_i
全局截止 = s_1 + 3X
```

**可推导结论**：由滚动关系，最后一棒截止时刻恒等于 `s_1 + 3X`。换句话说——**全局就是一块 3X 的表在跑，快的人只是把时间让给后面**。这条要写进规则页，否则队员理解不了"为什么我做得快队友时间反而多"。

**状态机**
```
准备 → 第1棒答题中 ──交棒/配时耗尽──→ 第2棒答题中 ──→ 第3棒答题中 ──→ 交卷 → 成绩
                                          └─ 全局截止到 → 立即结束
```

**必须由后端做的**
- 单一时钟：倒计时以服务端时间为准，交接不停表。
- 权威交棒：交棒是服务端事件，切换答题人；客户端不能自行切换。
- 越权防护：非当前棒提交一律拒绝。
- 服务端判分。
- 掉线：比赛场景不暂停；掉线 30 秒未回 → 服务端自动提交该棒已答内容并按**交棒**处理（时间照走）。

**边界**
- 一棒提前答完 X 题 → 必须手动点"交棒"（不自动，留检查时间），配时照常流逝。
- 一棒配时耗尽 → 强制交棒，未答记 0。
- 全局截止到 → 直接结束，剩余未答记 0。

**判分**：默认同团队对抗（答对 4、答错 −1、不答 0），可配。

### 4.5 赛制 5 · 团队抢答（官方「极速对抗」环节）

**规则（v0.3 定）**
- 3 人一队，多队同场。
- **前 50% 提交且答对的队伍加分；后 50% 的队伍即使答对也不加分。**

**每题流程（服务端驱动）**
```
1. 广播题目（带 serverTime）
2. 缓冲期 buffer = 1000ms：禁止提交，等所有端渲染完成；此期间提交记"抢跑"，无效
3. 提交窗口 submitWindow = 20s：每队可提交一次，提交即锁（不可回改）
4. 窗口关闭（或全员已提交）→ 按服务端 receivedAt 升序排序
5. 名额 = 前 ceil(N/2) 个提交，N = 本题开始时在线队伍数
6. 名额内：答对 → 加分（默认 +4）；答错 → 0（默认不扣分，可配 −1）
   名额之外：无论对错，本题 0 分（名额不顺延）
7. 未提交：本题 0 分
8. 下一题
```

**为什么这样定义**
- 与"前 50% 提交且正确的加分"字面对应：两个条件同时满足才加分。
- 名额按**队伍总数**的一半算，不按提交数——否则"大家都不提交"时比例失去意义。
- 提交即锁，所以"抢"的代价是真实的：抢了答错，分数没了且可能被后面的人挤掉名额。

**可配置项**（官方细则未查到，故全部外置）
| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `buzz.buffer_ms` | 1000 | 缓冲期，防误触与渲染未完成 |
| `buzz.submit_window_sec` | 20 | 提交窗口 |
| `buzz.qualify_fill` | `strict` | 名额内答错是否顺延给后面答对者；`strict` 不顺延 |
| `buzz.correct_points` | 4 | 答对加分 |
| `buzz.wrong_points` | 0 | 答错扣分（可选 −1） |
| `buzz.qualify_ratio` | 0.5 | 加分名额比例 |

**公平性**
- 裁决只看**服务端收包时刻**，不看客户端时间戳。
- 已知局限：网络延迟差会让快网队伍占优。默认**不做延迟补偿**，在规则页明示"本练习不消除网络差异"。
- 同毫秒或差值 < 5ms 视为并列，都计入名额，名额顺延但不超过 N。

**需要后端**：必须。

## 7. 架构与部署

### 7.1 总体结构

```
                    ┌──────────────────────────────────────┐
                    │ 前端（静态，GitHub Pages / 任意托管）    │
                    │  ┌──────────────┐  ┌───────────────┐  │
                    │  │ 静态对局引擎   │  │ 房间客户端(WS) │  │
                    │  │ 前端判分       │  │ 服务端判分     │  │
                    │  └──────────────┘  └───────┬───────┘  │
                    └───────────┬───────────────┼───────────┘
                                │ 构建期打包      │ https / wss
                     题库 JSON + 赛制参数          │
                                │                ▼
                                │      ┌────────────────────────┐
                                │      │ 对局后端（临时部署）      │
                                │      │ 房间 / 权威时钟 / 裁决    │
                                │      │ / 服务端判分             │
                                │      │ + 题库只读副本（热加载）  │
                                │      │ 内存态，无数据库          │
                                │      └────────────────────────┘
                                └──── 同一份 quiz JSON 目录（挂载/打包）────┘
```

### 7.2 分层原则

1. **引擎与运行模式分离**：赛制 = "状态机 + 规则"（纯逻辑，可单测）；运行模式 = "驱动它的人"（前端驱动 / 服务端驱动）。同一份规则跑两种模式。
2. **判分模块前后端共用**：一个纯函数包，前端 `import`，后端 `require`，杜绝两套规则漂移。
3. **服务端一旦启用，判分权归服务端**：因此后端加载只读题库副本（不是数据库、不接受写入）。
4. **参数只从服务端/构建产物读取**：客户端只能传 `paperId`，不能传时长、分值、题目列表。
5. **无状态之外只有房间**：房间是对局期间唯一内存状态，销毁即消失。

### 7.3 后端选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **Node + WebSocket（单文件服务）** | 最好懂、最好改；Docker/单文件双入口；Linux 与 Windows 都能跑 | 需要一台常开的机器 | **采用** |
| Cloudflare Workers + Durable Objects | 免运维 | 需账号；国内访问不稳；读本地 JSON 不便 | 备选 |
| Deno Deploy | 免运维、WS 原生 | 生态少 | 备选 |
| Supabase Realtime | 不写服务端 | 做不了权威裁决 | 不适用 |

### 7.4 部署形态一：Linux 服务器

适用：社团/学校有一台常开的 Linux 机器或云主机。

```
# docker compose up -d
services:
  arena:
    image: <自建镜像>
    ports: ["8080:8080"]
    volumes:
      - ./data/questions:/app/data/questions:ro   # 题库只读挂载，热加载
      - ./data/papers:/app/data/papers:ro
    environment:
      - MAX_TEAMS_PER_ROOM=8
      - MAX_CONNECTIONS=300
```

- Nginx 反代：`/` → 静态前端；`/ws` → 后端（需 `Upgrade`/`Connection` 头，`proxy_read_timeout` 加长）。
- HTTPS 必须（浏览器在非 localhost 下不允许 ws:// 混合内容 → 必须 wss://）。
- 进程管理：`docker compose` 或 `systemd`；日志到 stdout，`docker logs` 可查。
- 一键脚本 `deploy/linux.sh`：装 Docker → 拉配置 → 起服务 → 打印访问地址。

### 7.5 部署形态二：Windows 个人电脑

适用：教练自己的笔记本，课上临时开局，不依赖外网。

- 提供**单文件可执行**（Node SEA 或 `pkg` 打包）：双击 `arena-server.exe` → 控制台打印：
  ```
  ✅ 题库已加载：55 题（其中可判分 40 题）
  ✅ 服务已启动
     本机访问： http://localhost:8080
     局域网访问：http://192.168.1.23:8080   ← 发给学生
     房间入口： http://192.168.1.23:8080/?server=...
  ```
- 首次运行弹 Windows 防火墙提示，需允许专用网络（文档写清步骤，附截图位）。
- 题库目录与 exe 同级（`.\data\questions\`），拖入新 JSON 即热加载。
- 局域网内学生输 `http://192.168.1.23:8080` 即可；外网需内网穿透（文档给 frp / cloudflared 两种可选方案，不默认内置）。
- 一键脚本 `deploy/windows.ps1` + `启动.bat`：检测端口占用 → 起服务 → 自动打开浏览器。

### 7.6 静态前端

- `npm run build -w @aixx/web` → 产物放 GitHub Pages（与 `aixx-guide` 同仓、子路径发布）。
- 页面顶部"联机"入口：未配置后端时置灰并提示"需先部署后端（见文档）"。
- 配置优先级：`?server=` > localStorage > 构建默认值。
- **形态 D：静态前端 + 独立后端**。`?server=` 只接受 **origin**（如 `http://192.168.1.23:8080`），前端自行派生 `ws(s)://host/ws`。
- **混合内容硬限制**：https 页面连不上 `ws://`/`http://`（浏览器直接拦截）。
  | 前端来源 | 后端地址 | 可行性 |
  | --- | --- | --- |
  | `https://*.github.io` | `https://` 隧道（cloudflared / ngrok） | ✅ |
  | `https://*.github.io` | 局域网 `http://` / `ws://` | ❌ 被拦截；UI 明确提示"需 https 后端" |
  | 后端托管的页面（形态 B/C） | 同源 `ws(s)` | ✅ **平时练习推荐这个** |
- 服务端提供 `GET /healthz` 探活与 `--allow-origin <origin>` 白名单，默认仅同源。

## 9. 关键算法

### 9.1 客户端与服务端时间对齐

1. 连上后连续 3 次 `PING`，取最小 RTT 那次：`offset = serverTime + rtt/2 - localTime`。
2. 倒计时显示 `remaining = deadline - (localNow + offset)`。
3. 每 30 秒重校准；变化 > 500ms 时以服务端为准并平滑显示。
4. **所有"是否超时"的判断都在服务端**；客户端只负责显示。

### 9.2 接力赛时间继承

见 §4.4 公式。服务端在交棒事件里结算：
`carry = max(0, legBudget - (now - legStartAt))`，`nextBudget = X + carry`。
全局截止固定为 `startAt + 3X`。分棒按 `paper.legs[i]` 下发，交棒后前一棒的题不再下发。

### 9.3 抢答裁决（v0.3）

```
收到 SUBMIT(teamId, qid, choice)：
  if phase != answering(qid) → 丢弃
  if now < submitOpenAt        → 丢弃并记 "early_submit" 事件（缓冲期内提交）
  if 该队本题已提交             → 丢弃（提交即锁，只认第一次）
  record { teamId, qid, receivedAt: now, clientSentAt: 诊断用 }
  → 立即服务端判分，回 ACK(accepted, correct)（不回正确答案）

窗口关闭时：
  ranking = submissions 按 receivedAt 升序
  quota = ceil(N * qualify_ratio)        // N = 本题开始时在线队伍数
  for i, sub in ranking:
     if i < quota  → sub.awarded = sub.correct ? correct_points : (qualify_fill=="strict" ? 0 : 顺延)
     else          → sub.awarded = 0
  if qualify_fill == "fill": 名额内的错误答案把名额让给后面第一个正确答案，直至名额用满
```

> 默认 `strict`：名额内答错就是 0 分，机会不转给后面的队。

### 9.4 判分

| 题型 | 得分规则 |
| --- | --- |
| 单选 / 判断 | 选中唯一正确答案得满分，否则 0 或按配置扣分 |
| 多选 | 答案集合完全相等才得分；少选、多选、错选均不得分（按配置决定是否扣分） |
| 未答 | 按 `unanswered` 规则（默认 0） |

### 9.5 提交、幂等与断线（v0.3 定）

| 模式 | 行为 | 幂等 | 回改 |
| --- | --- | --- | --- |
| `batch`（赛制 1） | 逐题**静默上报**（服务端存答案、不回对错），交卷时统一判分 | `(sheetId, qid)` 去重，取最后一次 | ✅ 允许（截止前） |
| `stream`（赛制 2–5） | 每题提交即锁，服务端立即判分 | `(sheetId, qid)` 去重，取第一次 | ❌ 锁定后不可改 |

断线处理（v0.3）：
- 客户端把未确认提交放进本地队列（IndexedDB），重连后按 `seq` 补发。
- **30 秒内连回**：继续答题，补交成功，复盘标黄。
- **超过 30 秒未连回**：服务端**自动提交该选手/该队已答内容**（不作废），并结束其作答资格；接力赛中按交棒处理，时间照走。
- 服务端判"超时"用收包时刻；宽限期内补交也接受。

## 12. 风险与已知坑

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **题库答案缺失** ✅ 已解除 | 原为最大阻塞 | 87 道 verified 已导入；后续新增题按同一套 schema 与校验脚本入库 |

| 官方细则缺失 | 接力/抢答的题量、时长、计分公开材料未查到 | 全部参数化；拿到官方规程后只改 JSON |

| Windows 防火墙 | 学生连不上局域网地址 | 启动脚本检测并提示放行；文档附步骤 |

| 多队房间权限 | 房主/队长/主答三层权限 | 先写权限矩阵再写代码 |

| AC-14 纠错反馈 | 静态模式点"这题有误" | 打开预填好的 GitHub Issue；房间模式写入对局日志 |
